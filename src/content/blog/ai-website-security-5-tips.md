最近 PHP、Java、Go 接連發布緊急安全更新。PHP 這次出現可能讓駭客遠端執行程式的漏洞，Java、Go 則因為 HTTPS 憑證信任的問題緊急更新。

這提醒我們一件事：**用 AI 做出網站，不等於能安全上線。**

這篇整理 5 個沒學過程式也能先檢查的重點，最後附上：

- **上線前資安健檢 Checklist**：一項一項打勾，也附上可以直接貼給 Claude Code 或 Codex、讓 AI 幫你掃整個專案的 Prompt
- **commit 前自動擋金鑰**：讓電腦以後每次存檔前都自動檢查，不用靠記性

## 一、API Key 別公開

API Key 就像付費服務的鑰匙。你用 AI 串接寄信、地圖或 AI 服務時，如果金鑰被拿走，別人就能用你的額度，帳單算在你頭上。

**私密金鑰放在後端**，用環境變數或專門保管秘密的服務存放，不要寫進網頁程式，也不要放進公開的 GitHub 專案。

特別注意變數名稱的前綴。用 Next.js 或 Vite 做網站時，金鑰通常放在 `.env` 檔裡，網站打包時有一條規則：

- 沒有前綴的變數只留在伺服器上，訪客拿不到
- `NEXT_PUBLIC_`、`VITE_` 開頭的變數代表「這個值可以公開」，會直接打包進網頁，任何人按 F12 打開瀏覽器的開發者工具就看得到

這裡有個 AI 很常踩的陷阱：你請 AI 在網頁上加一個呼叫 AI 服務的功能，網頁讀不到金鑰、程式跑不起來，AI 為了讓它能跑，就把變數改成 `NEXT_PUBLIC_` 開頭。功能正常了，但金鑰也公開了。

正確做法是把呼叫外部服務的程式放在後端，網頁只跟你自己的後端溝通。判斷標準很簡單：**這個值被陌生人拿到，會不會花到你的錢、碰到你的資料？** 會的話，就不能加這種前綴。

用 Supabase 的話，要分清楚兩把金鑰：

- **anon key（publishable key）**：設計上就會出現在前端，看到它在網頁裡不用慌，安全靠的是第四點的 RLS
- **service_role key（secret key）**：可以繞過所有權限規則，**絕對不能出現在前端或公開的 repo**

`.env` 是常見的設定檔，裡面通常放著金鑰，要加入 `.gitignore` 避免上傳。也要檢查過去的 Git 紀錄，確認它從來沒有被上傳過。

**已經外洩，就立刻去該服務撤銷、換一把新的。** 只把檔案刪掉沒有用，舊金鑰不會因此失效，Git 紀錄裡也還找得到。

## 二、Prompt 和 Git 紀錄也會被看見

先解釋兩個名詞：

- **repo**：存放專案的地方，例如 GitHub 上的一個專案
- **Git 紀錄**：Git 會留下每次修改的內容與時間，連你後來刪掉的舊版本都留著

正常情況下，你在對話框裡打給 AI 的 Prompt，不會進到專案裡。但最近的選舉網站事件，就是 Prompt 被一起傳上了公開的 repo，再加上 Git 的時間紀錄，整個開發過程都被攤開來看。

Prompt 怎麼會跑進專案？常見有三種情況：

- **對話紀錄被存成檔案**：有些 AI 工具或擴充套件，會自動把你跟 AI 的對話存成檔案，放在專案資料夾裡
- **需求文件**：你請 AI 把需求整理成 `task.md` 或規格書，裡面寫著你的指令、客戶需求，甚至測試帳號
- **AI 工具的設定檔**：像 `CLAUDE.md`、`AGENTS.md` 這種給 AI 看的說明檔，本身就是 Prompt，而且通常會跟著專案一起上傳

這些檔案只要沒被排除，commit 時就會一起存檔，push 時就會一起上傳。

- 客戶資料、內部需求、測試帳密，不要寫進 Prompt 和文件，也不要貼給公司沒核准的 AI 服務
- AI 工具自動產生的對話紀錄資料夾，加進 `.gitignore`，不要上傳
- 每次 push 前，請 AI 檢查這次要上傳的內容裡，有沒有對話紀錄、客戶名稱、內部專案代號或測試帳密。文章後面的「push 前再請 AI 看一眼」Prompt 已經包含這一步
- 查到外洩的帳密，先撤銷換新

## 三、密碼不能存明文

有會員登入畫面，不代表密碼有被好好保護。如果資料庫直接存使用者原本的密碼，資料一被偷，使用者在其他網站用同一組密碼的帳號也會跟著受害。

密碼要「**存果汁，不存水果**」：把密碼打成果汁再存。

登入時，把使用者輸入的密碼再打一次，果汁一樣就放行。資料庫被偷，對方拿到的也只是果汁，倒不回原本的密碼。這個「打成果汁」的動作，技術上叫做**雜湊（hash）**。

- 密碼請 AI 用 **bcrypt** 或 **Argon2id** 這類專門處理密碼的雜湊方式，不要用 MD5、SHA-1 這種太快的
- 更省事的做法是直接用 Supabase Auth 這類現成的登入服務，不要自己做密碼處理
- 姓名、電話、地址這些個資，因為之後還要讀出來使用，不能 hash，做法是**少存、加密、控管誰能看**

## 四、登入了不代表看不到別人的資料

假設你做了一個預約網站。A 登入後，把網址裡的預約編號改成 B 的，就看到了 B 的姓名和預約內容。

這代表網站有確認「你是誰」，卻沒有確認「這筆資料是不是你能看的」。這是 AI 寫出來的網站最常見的漏洞之一，技術上叫 IDOR 或越權存取。

- 後端每次讀取、修改資料，都要確認這個使用者有沒有權限；只在畫面上把按鈕藏起來不夠
- 準備兩個測試帳號，互相試著讀取、修改對方的資料，確認都會被擋下

用 Supabase 的話，要檢查 **RLS（Row Level Security，資料列權限規則）**。它用來限制每個使用者能讀取、修改哪些資料。

- 每一張存放使用者資料的表都要開啟 RLS
- 開啟後還要確認規則設對了；沒有規則的表等於誰都不能讀，規則寫太寬等於誰都能讀
- RLS 規則常常是在 Supabase 後台設定，不在程式碼裡，AI 掃專案不一定看得到，記得自己進後台確認

## 五、上線不是終點

PHP、Java、Go 這次的事件提醒我們：**你沒改任何程式，底層還是會出漏洞。** 網站用到的套件、執行環境，都需要持續維護。

- 在 GitHub 開啟 **Dependabot**，接收套件漏洞與更新通知
- 定期檢查並更新套件和執行環境，不要只等通知
- 重大漏洞要及時修補，測試功能正常後再重新部署

## 上線前資安健檢 Checklist

上線前，照著下面一項一項確認：

**一、API Key**

- [ ] 私密金鑰都放在後端，沒有寫進網頁程式
- [ ] 沒有私密金鑰用 `NEXT_PUBLIC_`、`VITE_` 開頭命名
- [ ] `.env` 已加入 `.gitignore`，Git 紀錄裡也從來沒出現過
- [ ] 曾經外洩的金鑰，都已經撤銷、換新

**二、Prompt 和 Git 紀錄**

- [ ] 專案裡的文件、AI 設定檔，沒有客戶資料、內部需求或測試帳密
- [ ] AI 工具自動產生的對話紀錄，沒有被上傳

**三、密碼與個資**

- [ ] 密碼用 bcrypt、Argon2id 處理，或交給 Supabase Auth 等現成登入服務
- [ ] 個資只存必要的，並有加密與權限控管

**四、資料權限**

- [ ] 用兩個測試帳號互相試過，讀不到、也改不了對方的資料
- [ ] 用 Supabase 的話，每張存放使用者資料的表都開了 RLS，規則也確認過
- [ ] Supabase 的 service_role key 沒有出現在前端

**五、上線後維護**

- [ ] GitHub 已開啟 Dependabot
- [ ] 有固定的時間檢查、更新套件

### 懶得一項一項查？交給 AI

下面這段 Prompt 會讓 AI 把你的專案從頭掃一遍，依照上面 5 關產出一份報告。

使用方式：

1. 在 Claude Code 或 Codex 開啟你的網站專案
2. 先切到唯讀模式，讓 AI 在這個模式下不能修改任何檔案，這比只在 Prompt 裡要求「不要改」更可靠
   - Claude Code：按 `Shift+Tab` 切換到 **Plan mode**（畫面下方會顯示 plan mode）
   - Codex：把權限切成唯讀（Read Only）模式
3. 貼上下面的內容送出，先讀完報告，再決定要修哪些

```txt
你是一位資深 Web Application Security Engineer。
請對目前這個網站專案進行「唯讀」資安檢查，先產出報告，不要修改任何檔案、提交 Commit、部署，或把專案內容上傳到外部服務。
可以執行 npm audit、pip-audit 等官方套件漏洞查詢指令，以及 git log 等唯讀指令。

請檢查以下範圍：

1. API Key / Secret / Token 洩漏
   - 檢查原始碼、.env、設定檔、README、前端打包產物及 Git 歷史。
   - 判斷秘密是否會進入瀏覽器端（例如 NEXT_PUBLIC_、VITE_ 開頭的變數，特別留意是否為了讓前端能讀取而把私密金鑰改成這種開頭），或被提交至公開 Repository。
   - 確認 .env 等檔案已列入 .gitignore，且從未被提交過。
   - 不要在報告中輸出完整金鑰；若發現疑似外洩，列出檔案路徑與安全的修復建議（包含撤銷／輪換金鑰）。

2. Prompt / 文件 / 開發歷史中的機密
   - 檢查 CLAUDE.md、AGENTS.md、README、Markdown 文件、提示詞檔案與開發紀錄，是否包含客戶個資、內部需求、合約、測試帳密等敏感資訊。
   - 指出可能外洩的位置，不要把機密內容複製到報告。
   - 不要讀取與目前專案無關的檔案。

3. 密碼與個資安全
   - 檢查密碼是否以 Argon2id、bcrypt 或等效的專用密碼雜湊機制保存；確認沒有明文密碼或 MD5、SHA-1 等不適合的快速雜湊。
   - 對姓名、電話、地址等需要讀取的個資，檢查加密、最小權限、保存方式與是否真的需要保存。
   - 若由第三方登入服務管理（例如 Supabase Auth），描述責任邊界與仍需檢查的設定。

4. 身分驗證與越權存取
   - 檢查 API、Server Actions、後端與資料庫是否在伺服器端驗證使用者身分及資料所有權。
   - 設計兩個測試帳號 A / B 的 IDOR / BOLA 測試案例，確認無法跨帳號讀取與修改資料。
   - 如果使用 Supabase：檢查程式碼與 migration 中的 RLS 設定；確認 service_role（secret）金鑰沒有出現在前端；若 RLS 規則可能是在後台設定、無法從程式碼確認，請列入「需人工驗證」。
   - 只提出安全的驗證方案，沒有明確授權不要對正式環境執行任何攻擊測試。

5. 套件與執行環境安全
   - 盤點框架、依賴套件、Runtime 和容器映像版本，檢查已知漏洞及修補建議。
   - 區分已確認的漏洞、疑似風險與無法確認的項目。
   - 提出回歸測試與重新部署的建議，不要直接升級。

請用下列欄位輸出報告：
- 編號
- 風險等級：Critical / High / Medium / Low
- 問題描述與影響（請用沒學過程式的人也看得懂的說法）
- 發現位置（檔案路徑／元件，不輸出秘密本身）
- 證據或驗證方法
- 建議修復方式
- 是否已確認：已確認／待驗證／無法確認

最後整理：
A. 上線前必修項目（Blocking）
B. 可排入後續修正的項目
C. 需要我補充的資訊或人工驗證項目

務必保持唯讀。先回報結果，等待我審核後再進行修改。
```

健檢結果仍然需要人工確認。AI 可能漏掉問題，也可能把沒問題的地方誤報成風險。

## 讓電腦每次存檔前自動擋下金鑰

健檢是上線前做一次。但金鑰外洩常常發生在平常不小心的時候，例如某天測試時把金鑰直接貼進程式，忘了拿掉就上傳了。

這種事靠記性擋不住，比較好的做法是**讓電腦每次都自動檢查**。

### 先用白話搞懂三個詞

如果你沒碰過 Git，可以先這樣理解：

| 詞 | 白話 | 比喻 |
| --- | --- | --- |
| commit | 在自己電腦上建立一個存檔點 | 遊戲存檔 |
| push | 把存檔上傳到 GitHub 等雲端 | 把存檔上傳到雲端 |
| hook | 在 commit 或 push 前自動執行的檢查 | 機場安檢門 |

我們要裝的是 **pre-commit hook**：每次 commit 之前，自動檢查這次要存的內容裡有沒有金鑰，有就擋下來，不讓你存檔。

為什麼擋在 commit，不等到 push？因為金鑰只要進了存檔紀錄，就算之後刪掉，紀錄裡還是找得到，清起來很麻煩。**在存檔前就擋下來最乾淨。**

### gitleaks 是什麼

檢查用的工具是 [gitleaks](https://github.com/gitleaks/gitleaks)，一個免費、開源的金鑰偵測工具。它認得上百種服務的金鑰長相，全部在你自己的電腦上檢查，不會把程式碼上傳到任何地方，而且一秒內就跑完，每次 commit 都跑也不會覺得卡。

它只認得「長得像金鑰的字串」，`admin1234` 這種普通密碼，或第四點那種權限問題，它都看不出來。所以它是第一道防線，不是全部。

### 設定 Prompt

你不需要自己學怎麼設定，把下面這段貼給 Claude Code，它會一步一步帶你完成。安裝軟體前它會先問你。

```txt
請幫我在目前這個專案加上「commit 前自動檢查金鑰」的機制。我沒有學過程式，請每一步都用白話說明你在做什麼、為什麼要做。

規則：
- 安裝任何軟體、或修改這個專案以外的設定之前，先告訴我要做什麼、為什麼，等我同意再做。
- 不要幫我 commit 或 push，也不要刪除任何既有檔案。
- 不要在畫面上顯示完整的金鑰；如果發現疑似金鑰，只顯示檔案位置和服務種類。

步驟：
1. 確認環境
   - 確認目前資料夾是不是 Git 專案。如果不是，先用白話解釋 Git 是什麼，問我要不要初始化，不要自己決定。
   - 確認我的作業系統（Windows / macOS / Linux），以及是否已經安裝 gitleaks。
   - 確認專案是否已經在用 husky、lefthook、pre-commit 等 hook 工具，或已經設定過 core.hooksPath。如果有，改成整合進現有設定，並先告訴我你打算怎麼做。

2. 安裝 gitleaks
   - 依我的作業系統建議最簡單的官方安裝方式（例如 macOS 用 Homebrew、Windows 用 winget），等我同意後再安裝。
   - 安裝後執行 gitleaks version 確認成功。

3. 建立 pre-commit hook
   - 在專案裡建立 .githooks/pre-commit，在 commit 前只掃描這次要 commit 的內容（staged changes），並遮蔽金鑰內容。
   - 依安裝的 gitleaks 版本選擇正確指令：先試 gitleaks git --help，能執行就用新版指令 gitleaks git --pre-commit --staged --redact --no-banner -v，不能就用舊版指令 gitleaks protect --staged --redact --no-banner -v。一定要加 -v，才會列出是哪個檔案、哪一行有問題。
   - 發現金鑰時要擋下 commit，並用中文印出：哪個檔案有問題，以及該怎麼處理（把金鑰移到 .env、如果已經上傳過就去該服務撤銷換新、確定是誤判可以在該行加上 gitleaks:allow 註解）。
   - 如果電腦上找不到 gitleaks，要印出中文提醒並擋下 commit，不要默默放行。
   - 確認 hook 檔有執行權限，再執行 git config core.hooksPath .githooks 啟用它。

4. 檢查 .gitignore
   - 確認 .env、.env.local 等存放金鑰的檔案已經列在 .gitignore；沒有的話補上。
   - 用 git ls-files 檢查這些檔案是不是早就被 Git 追蹤了；如果是，告訴我，不要自己處理。
   - 檢查專案裡有沒有 AI 工具自動產生的對話紀錄資料夾或檔案（例如 .specstory 這類存放聊天紀錄的資料夾）。有的話告訴我，問我要不要加進 .gitignore。

5. 掃描過去的紀錄
   - 用 gitleaks 掃描整個 Git 歷史（加上 --redact），列出結果。
   - 如果有發現，告訴我是哪一種服務的金鑰、在哪個檔案，並提醒我：從紀錄裡刪掉不夠，要先去該服務撤銷、換新。

6. 實際測試
   - 建立一個測試檔，放一組假的金鑰：用隨機產生、格式像 GitHub token 的字串（ghp_ 加 36 個英數字），不要在字串裡寫 fake、test 這類字，否則 gitleaks 可能直接忽略。加入暫存區後嘗試 commit，確認會被擋下，而且有列出檔案名稱。
   - 測試完把測試檔從暫存區移除並刪除，確認 git status 回到測試前的狀態。
   - 再暫時把 gitleaks 從 PATH 拿掉、直接執行 hook，確認找不到 gitleaks 時也會擋下並印出提醒。

7. 在 README 加一小段說明：這個專案有 commit 前的金鑰檢查；這個檢查只對這台電腦上的這份專案有效，換電腦或重新 clone 專案後，要先安裝 gitleaks，再執行一次 git config core.hooksPath .githooks。

最後用白話總結：裝了什麼、以後 commit 時會發生什麼事、被擋下來時我該怎麼做。也請提醒我：git commit --no-verify 可以跳過檢查，但那等於把安檢門拆掉，不要用它來繞過真的金鑰。
```

裝好之後，如果 commit 被擋下來，照畫面上的提示把金鑰移到 `.env` 再重新 commit 就好。不要叫 AI 幫你「跳過檢查」，那等於把安檢門拆掉。

### 我的實測結果

這段 Prompt 我在這個部落格的專案上實際跑過：

- 整個專案的歷史紀錄不到 1 秒就掃完，沒有發現外洩的金鑰
- 故意放一組假的金鑰再 commit，馬上被擋下來，畫面會告訴你是哪個檔案、第幾行
- 一般的修改正常通過，感覺不到多了一道檢查

實測時也踩到一個坑：照預設設定，被擋下時只會說「有問題」，不會說在哪個檔案。上面的 Prompt 已經修正這點，直接複製就好。

### 進階：push 前再請 AI 看一眼（選用）

gitleaks 只認得金鑰。像第二點的對話紀錄、客戶名稱，或第四點「改網址就看到別人資料」這種邏輯問題，它都看不出來，要靠 AI 審查。

AI 審查比較慢（幾十秒到幾分鐘），也會用到你的 AI 工具額度，所以不適合每次 commit 都跑。比較好的時機是 **push 前**，而且只檢查這次要上傳的修改。

另外，AI 的判斷不一定每次都一樣，也可能誤報。所以這一層**只提醒、不擋下**。如果設定成 AI 說有問題就不准 push，很快你就會習慣跳過檢查，整個機制就失效了。

Claude Code 和 Codex 都有「不用互動、跑完就結束」的模式，可以放進 hook 裡用。這段 Prompt 會先檢查你電腦上裝了哪一個，再用那一個來審查。

如果你想加，把下面這段貼給你平常用的 AI 工具：

```txt
請在目前專案的 .githooks/ 裡再加一個 pre-push hook：每次 push 前，請 AI 檢查這次要推上去的修改有沒有資安問題。我沒有學過程式，請用白話說明你在做什麼。

規則：
- 不要幫我 commit 或 push，也不要刪除任何既有檔案。
- 安裝任何軟體或修改專案以外的設定前，先問我。

要求：
- 先檢查我電腦上裝了哪些 AI 命令列工具：Claude Code（claude）、Codex（codex）。告訴我找到哪些，問我要用哪一個；hook 執行時如果找不到我選的工具，就改用另一個。
- 先用各工具的 --help 確認它目前版本的「非互動模式」與「唯讀／限制權限」參數（例如 claude -p、codex exec 搭配唯讀沙箱），不要憑記憶寫參數。
- 只檢查這次要 push 的 commit 差異：先讀完 Git 從 stdin 傳進來的 ref 資訊，用 remote 與 local commit 計算 diff，不要掃整個專案。新分支在遠端還沒有 commit 時，就和預設分支比較。
- diff 是空的就直接跳過。
- 只把 diff 當文字交給 AI 看，不要給它修改檔案或執行指令的權限（也避免它在 hook 裡執行 git，造成重複觸發）。
- 先問我有哪些不能公開的關鍵字（例如客戶名稱、內部專案代號），存在專案裡一個本機檔案，並把這個檔案加進 .gitignore，確保關鍵字清單本身不會被上傳。
- 請 AI 找出：寫死的金鑰、沒有檢查權限的 API（越權存取）、SQL injection、XSS、把私密設定放到前端；以及這次要上傳的檔案裡，有沒有 AI 對話紀錄、Prompt 草稿、測試帳密，或出現在關鍵字清單裡的字。輸出用中文條列，每一條附上檔案位置和風險等級；沒有發現就說沒有。
- 只提醒、不擋下：不論結果如何，hook 都要讓 push 繼續（exit 0）。審查超過 3 分鐘、找不到任何 AI 工具，或工具沒有登入，就跳過並印出中文提醒。
- 設定環境變數 SKIP_AI_REVIEW=1 時跳過審查。
- 加好後，直接執行這個 hook 腳本模擬一次給我看，不要真的 push。
- 在 README 的 hook 說明裡補上這一段的用途、用的是哪個工具，以及跳過方式。

最後用白話總結：以後 push 時會看到什麼、看到警告時我該怎麼判斷。
```

幾個小提醒：

- 從 VS Code、GitHub Desktop 這類圖形介面 push 時，hook 可能找不到 AI 工具或拿不到登入狀態，這時只會印出提醒並跳過。想確實看到審查結果，就在終端機裡 push。
- 每次 push 都會用到該工具的額度，修改量大時也要多等一下。

注意：這一層會把你的程式修改內容送給 AI 服務審查。如果是公司的專案，請先確認公司是否允許把程式碼交給外部 AI 服務。
