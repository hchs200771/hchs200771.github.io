[上一篇健檢](/blog/seo-aeo-for-personal-site/)補了分享圖、結構化資料、RSS 與自動產生的 llms.txt，網站的基本功已經有了。

過了一個多月，網站多了幾篇文章。我再請 AI 分別用「搜尋引擎」與「AI 助理」兩種讀者的角度檢查，而且這次不只讀原始碼，也實際去抓線上的網址。

SEO 是讓搜尋引擎更容易理解網站；AEO（答案引擎最佳化，也有人叫 AIO、GEO）則是讓 AI 助理更容易讀取、理解與引用內容。

**這次找到的缺口，集中在錯誤頁、更新訊號、單篇內容與作者辨識。以下都是健檢結果與打算採用的修法，目前還沒修，不是完成報告。**

## 一、先看第二輪的結果

這份紀錄以 2026-11-11 健檢時、本站原有的六篇文章為基準，不包含同日準備新增的文章。線上回應也以當次實測為準。

做得好的部分先帶過：canonical（標準網址）、OG 分享資訊、BlogPosting／BreadcrumbList／WebSite／Person 結構化資料、RSS、自動產生的 llms.txt 與 llms-full.txt 都有，robots.txt 也全部允許。這些怎麼做，上一篇已經講過。

這輪依我判斷的影響大小，整理成以下待辦；不是搜尋排名權重的實測結果。

| 項目 | 現況 |
| --- | --- |
| 自訂 404 頁 | 缺 |
| sitemap 最後更新日期 | 缺 |
| 單篇 Markdown 網址 | 缺 |
| 每篇獨立分享圖 | 缺 |
| 作者資料與關於頁標記 | 偏弱 |
| 標題與描述長度 | 偏長 |
| 開頭摘要與問答 | 待補 |
| 標籤頁與延伸閱讀 | 缺 |
| 圖片尺寸與處理 | 待補 |
| 驗證標籤與流量量測 | 原始碼看不到 |
| 自有網域 | 尚未換 |
| 標點、RSS 全文與 OG 圖尺寸 | 待補 |

**第一輪確認「有沒有」，第二輪開始看「有了之後，內容是否夠完整」。**

## 二、沒有自己的 404 頁

`src/pages/` 目前沒有 `404.astro`。線上打開一個不存在的網址，回的是 GitHub Pages 預設英文「Page not found」，沒有本站導覽列，也沒有回首頁的連結。

404 就是「找不到這一頁」。讀者可能從過期連結進來，也可能只是網址打錯；現在不只找不到內容，連下一步去哪裡都沒有提示。

對爬蟲來說，404 狀態本身是正確訊號；對訪客來說，**找不到這頁，不該等於離開整個網站。**

我打算新增 `src/pages/404.astro`，沿用 `Base` 版型，說明頁面不存在，放回首頁、最新文章與作品的連結。部署後還要再打一個不存在的網址，確認顯示自訂內容，HTTP 狀態仍是 404。

## 三、Sitemap 沒有最後更新日期

Sitemap 是列給搜尋引擎看的網址清單。線上的 `sitemap-0.xml` 目前每個 `<url>` 只有 `<loc>`，沒有表示最後更新日期的 `<lastmod>`。

本站的 frontmatter 雖然支援 `updatedDate`，但健檢時六篇文章都沒填。像資安五秘訣發佈後已修訂過兩次，機器卻只能讀到原本的發佈日期。

最後更新時間能提供重抓頁面的線索，但不保證搜尋引擎一定採用。**日期要反映內容的實質變動，不能每次 build 都把全部文章洗成今天。**

我打算分兩步改：

- 文章有實質修訂時，依真實修改日期填 `updatedDate`，不要憑印象補日期
- 讓 sitemap 產生流程依文章網址帶出 `updatedDate`，未更新的文章用 `pubDate`；其他頁面另訂可查證的更新依據

目前 `astro.config.mjs` 只是呼叫 `sitemap()`，還沒有文章日期對應。實作時會先核對專案使用版本支援的整合方式，再檢查產出的 XML，不在這裡先寫未驗證的設定。

## 四、每篇文章沒有 Markdown 版網址

Markdown 是用純文字標記標題、清單與連結的格式。llms.txt 提案建議，頁面可以另提供 `.md` 版本，方便 AI 直接讀內容。

目前本站有整站合併的 `llms-full.txt`，但實測 `/blog/<slug>.md` 是 404。AI 助理只想讀一篇文章時，仍得解析包含導覽列、頁尾的 HTML。

**整站全文適合一次掌握內容，單篇 Markdown 適合精準讀取。** 兩者可以一起存在，但提供了也不代表所有 AI 都會自動採用。

我打算增加產生 `/blog/[slug].md` 的端點：

- 從 blog 內容集合產生每篇非草稿文章的網址
- 沿用 `src/llms.ts` 的 `toPlainMarkdown`，處理 MDX 的 import 與互動元件
- 保留標題、摘要、作者、日期與原文連結，回傳 UTF-8 的 Markdown 內容
- 把 llms.txt 的文章連結改指向 `.md` 版，同時保留 HTML 原文的入口

這是預定做法，端點目前還不存在。改好後要同時核對內容、回應類型，以及文章裡的連結和圖片路徑能不能正確解析。

## 五、每篇文章的分享圖都一樣

健檢時六篇文章都沒有填 `cover`，所以分享到 LINE 或 Facebook，全都使用同一張預設圖。圖是有了，但看不出分享的是哪篇文章。

這主要影響分享時的辨識與閱讀意願，不能直接當成排名提升的保證。

我打算在 build，也就是網站建置時，依每篇標題自動產生 1200×630 分享圖，維持固定字體、配色與作者資訊，讓長標題能自動換行。

**預設圖繼續當備用，每篇文章則有自己的辨識。** 實作後還要用實際分享預覽確認裁切與中文字體，不能只看產出的檔案尺寸。

## 六、作者資料太單薄

`src/layouts/Base.astro` 的 Person JSON-LD 目前有 `name: "Max"`、英文 `jobTitle` 與社群連結，但 `description` 沿用整個網站的描述，沒有照片，也沒有 `knowsAbout` 專長主題。

JSON-LD 是把頁面資訊用固定格式寫給機器看的資料。「Max」是常見名字，只靠名字，AI 很難把我跟其他 Max 區分開。關於頁目前也沒有 `ProfilePage` 標記，明確說明這是個人介紹頁。

我打算補上個人專屬描述、照片 `image`，以及 AI Coding、Vibe Coding、後端開發等 `knowsAbout` 主題。關於頁再加 `ProfilePage`，連回全站既有的同一個 Person 識別。

**資料要能對上畫面上的自我介紹與真實經歷。** 我是後端工程師出身的 AI Coding 教練，不能為了看起來專業，就塞入沒有依據的頭銜或專長。

## 七、標題、摘要與站內連結再整理

這幾項比較偏向內容編輯與閱讀動線，我打算一起整理。

- **標題與描述偏長**：目前瀏覽器標題是「文章標題 | Max | AI Coding 教練」，文章標題常有 25–30 個中文字；資安五秘訣的 description 超過 100 字。搜尋摘要可見範圍會隨裝置與查詢改變，大約前 80 字應先說結論。文章頁後綴打算縮成「| Max」。
- **開頭沒有先講答案**：目前多半先鋪陳再進正題。我打算在每篇開頭補 2–3 句能獨立理解的重點，方便讀者快速判斷，也讓 AI 比較容易擷取完整意思。
- **適合的文章補常見問題**：用問句當小標題，第一句就回答，再補限制與例子。這是改善內容可讀性，不代表加了 FAQ 結構化資料就會有搜尋結果特殊樣式。
- **站內連結只靠手動**：目前沒有標籤頁，文章底下也沒有自動延伸閱讀。資訊安全、Vibe Coding、Claude Code、Cloudflare 等共同標籤，打算用來產生標籤頁與相關文章。

**摘要要能獨立回答問題，延伸閱讀則要真的相關。** 不需要每篇硬湊問答，也不用為了增加連結，把所有文章都塞在一起。

## 八、圖片、量測與網域

作品集卡片 `src/components/PortfolioCard.astro`，以及作品頁 `src/pages/portfolio/[slug].astro` 的 `<img>` 目前都沒有 `width`／`height`。

圖片載入前沒有預留尺寸，可能造成 CLS，也就是載入過程中版面突然位移。這是程式碼可見的風險，這次沒有量測 CLS 分數。

圖片目前放在 `public/`，直接複製到網站，沒有經過圖片處理流程；最大的一張 PNG 約 337KB。我打算改用 Astro 內建的 `astro:assets` 圖片處理，安排尺寸、壓縮與格式轉換，再檢查清晰度與版面。

量測方面，**原始碼裡看不到搜尋引擎網站驗證標籤，也看不到流量分析。** 但驗證也可能透過 DNS 或其他方式完成，不能因此斷言沒有註冊過。

我打算先確認 Google Search Console、Bing Webmaster Tools 是否已設定，未設定就補上。部分 AI 搜尋會用到 Bing 的索引，所以不只看 Google；再加入不用 cookie 的輕量流量分析，觀察來自 AI 助理的來源，但來源資料未必涵蓋每次 AI 引用。

另外，`astro.config.mjs` 與 `robots.txt` 都還留著「買好網域後要換」的 TODO，目前仍使用 github.io 網域。

網域是連結與引用累積的地址。**越晚搬家，需要整理的舊連結越多。** 我打算提早決定自有網域，遷移時一起處理 canonical、sitemap、robots 與可行的舊址導向。

## 九、幾個小細節也列入待辦

這些問題可以一起補，但目前也都還沒改：

- `src/consts.ts` 的網站描述混用半形逗號，會原樣出現在搜尋摘要與 llms.txt；打算統一中文標點
- RSS 目前只有摘要，打算評估提供全文，讓閱讀器使用者不用跳回網站也能讀完
- `og:image` 沒附寬高，打算補上實際尺寸，讓分享平台取得更完整的圖片資訊

**小細節不必搶在主要缺口前面，但要有地方記錄。** 否則每次健檢都會重複看到同一批問題。

## 十、這次健檢和上次有什麼不同

上次主要補程式碼裡缺的基本設定，這次還請 AI 實際抓線上的不存在網址、sitemap 與單篇 `.md` 網址。

原始碼可以提示「可能沒做」，但看不出部署後到底回什麼。GitHub Pages 的預設 404、線上 sitemap 實際有沒有日期、`.md` 路徑最後是不是 404，都要看 HTTP 回應，也就是伺服器真正送回來的結果。

**健檢要看「部署出去的結果」，不只看程式碼。** 本機建置成功，也不代表線上的路徑與內容就一定正確。

下面是可直接複製的第二輪健檢 Prompt 範本；執行時需讓 AI 有讀取線上網址的能力：

```text
請對目前網站做第二輪 SEO／AEO 健檢，保持唯讀，不修改檔案、不 commit、不部署。
先讀上一次健檢紀錄與目前原始碼，區分已做好的基本功和仍有缺口的部分。
再實際請求正式網站的以下網址，不要只推測原始碼部署後的結果：
- /robots.txt
- /sitemap-index.xml，以及它列出的 sitemap
- /llms.txt
- 一個不存在的網址
- 一篇文章頁，以及對應的 /blog/<slug>.md
記錄 HTTP 狀態碼、相關回應標頭與內容證據；無法連線就標明無法驗證。
分別以搜尋引擎與 AI 助理的角度檢查內容發現、更新日期、作者、摘要、圖片與連結。
依影響排序，每項附現況、為什麼重要、證據（檔案位置或實際回應）與建議修法。
區分已確認、推測與需人工確認的項目，不保證排名或 AI 引用成效。
確認目前框架與套件版本支援修法，不要編造設定 API。
先產出報告，不要直接改。
```

## 小結：第二輪檢查清單

接續上一篇的八點基本功，第二輪我會檢查：

- [ ] 不存在的網址，有自己的 404 與返回網站的入口
- [ ] 真正更新的文章有日期，sitemap 能反映實質更新
- [ ] 單篇文章有可讀的 Markdown 版，並核對部署後的回應
- [ ] 分享圖能分辨文章，作者資料能對上真實介紹
- [ ] 標題與摘要先說重點，標籤與延伸閱讀串起相關內容
- [ ] 圖片預留尺寸，並安排壓縮與格式處理
- [ ] 確認搜尋工具與流量量測，提早決定網域
- [ ] 修完再抓線上網址，保留實際回應作為驗證

上面這些問題目前都還沒修。我會依順序處理，修完再回來更新這篇，記錄哪些已完成、哪些還有平台限制。
