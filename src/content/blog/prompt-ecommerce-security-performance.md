電商是「錯一次就賠錢」的系統：超賣要處理客訴，重複收款要退款，會員資料外洩會失去信任。

我做的網站叫[海風日常](/portfolio/ecommerce-shop/)，全站跑在 Cloudflare。程式幾乎都由 AI 寫：Claude Code 負責規劃，Codex 負責實作，我負責下指令、做決定、驗收。

**AI 寫得出電商網站，但它不會主動把資安與效能顧到位。這兩件事，要寫進 Prompt 當成需求。**

我是後端工程師出身的 AI Coding 教練。這篇整理開發過程與 Prompt；想看庫存、訂單與登入的設計細節，可以接著讀[前一篇技術拆解](/blog/cloudflare-ecommerce-security/)。

下面標「範本」的是整理後可套用的指令；標「實際下的 Prompt」的才是當時原文。

## 一、先要規劃，不要先要程式碼

專案第一個 commit 是 2026-09-30 的 `docs: add Cloudflare-based architecture plan`，先有架構規劃文件，之後才有程式。

開發順序很清楚：

- 9/30：M0 骨架 → M1 會員與商品 → M2 購物車、庫存預留、待付款訂單
- 10/1：前台設計
- 10/12：M3 綠界信用卡付款

里程碑就是把大專案切成能單獨驗收的小階段。README 每一階段都有「完成標準」：M2 是「能建立 `pending_payment` 訂單且不超賣」，M3 是「綠界測試環境能完成一筆付款」。

**「做完購物車」太模糊；「下單不超賣」才知道要驗什麼。** 我會先用這個範本：

```text
我要做一個電商網站。請先寫架構文件，不要先寫程式。
列出前台、後台、API、資料儲存、庫存與金流的技術選型，每項附理由。
把開發切成可依序驗收的里程碑，每階段都寫明完成標準與驗證方式。
列出平台限制、已知風險、尚待我決定的取捨，以及暫時不做的功能。
先讓我看懂計畫，再進入實作。
```

## 二、把資安寫進需求

只說「幫我做登入」，AI 容易交出能動的版本。把安全條件說清楚，它才有明確的交付標準。

雜湊是把原始資料轉成不能直接還原的值；Session 是伺服器辨認登入狀態的憑證；schema 則是輸入資料必須符合的格式規則。不熟這些詞，可以先請 AI 解釋再做決定。

下面是資安需求的範本：

```text
請把以下條件當成必要需求，不是做完功能才補：
- 密碼使用專用雜湊演算法，每個帳號使用隨機鹽值。
- 伺服器只存 Session token 的雜湊，不存可直接登入的原始 token。
- Cookie 設定 HttpOnly、Secure、SameSite。
- 權限檢查做在 API，不能只藏畫面上的按鈕。
- 所有輸入用 schema 驗證，SQL 查詢一律參數化。
- 上傳採格式與大小白名單，檔名由伺服器產生。
- 錯誤回應不外洩內部細節；登入與註冊需要限流。
- 查詢別人的資料回 404，不透露資料是否存在。
每一項都要有對應的自動化測試。
平台有限制時，先告訴我取捨，不要默默降低安全條件。
```

這次有三個具體成果：

- **密碼用 PBKDF2-SHA256 加鹽**：AI 說明 bcrypt／argon2 的 CPU 成本不適合這個 Workers 執行模型，改採平台原生支援的方式。這是本專案的取捨，不是所有網站的通用答案。
- **KV 只存 Session token 的 SHA-256**：KV 是 Cloudflare 的鍵值儲存服務；外洩時不會直接拿到可登入的原始代碼。
- **帳號不存在，也跑一次雜湊**：減少從登入失敗的回應時間探測帳號是否存在的線索。

最後一點在 `apps/api/src/modules/auth/password.ts` 的實際程式碼如下：

```ts
export async function burnPasswordCheck(password: string): Promise<void> {
  await derive(password, new Uint8Array(SALT_BYTES), ITERATIONS)
}
```

**要求 AI 解釋取捨，也要求它交出測試。** 更多細節放在[原本的資安設計文章](/blog/cloudflare-ecommerce-security/)，這裡不重複展開。

## 三、效能也要用說的

效能不是最後加一句「幫我優化」。先告訴 AI 哪些內容要被搜尋、哪些資料不能過期，它才知道怎麼分配工作。

SSR 是伺服器先產生頁面內容，方便搜尋引擎讀取。海風日常的商品頁採這個方式；購物車、結帳、訂單是個人頁面，則只在瀏覽器渲染，規則寫在 `apps/storefront/nuxt.config.ts`。

其他設計也各有理由：

| 需求 | 我會怎麼跟 AI 說 | 實作結果 |
| --- | --- | --- |
| 前台讀 API | 服務之間直接溝通 | Service Binding 內部呼叫 |
| 商品圖快取 | 新圖用新網址，不覆寫舊圖 | R2 圖片以 UUID 命名 |
| 庫存正確 | 只讓同一規格排隊 | 每個規格一個 Durable Object |
| 控制讀取量 | 列表分頁並設上限 | pageSize 最大 100 |

Service Binding 是 Cloudflare 服務之間的內部通道，部署後前台呼叫 API 不經公開網路；本機開發才改走 HTTP。

R2 是存商品圖片的物件儲存服務。圖片檔名用 UUID 隨機識別碼、內容不變，回應帶 `cache-control: public, max-age=31536000, immutable`，讓瀏覽器能長期沿用。

Durable Object 是獨立管理狀態的物件。這裡每個規格各自管庫存，鎖的範圍只有該規格，不會全站排一條隊；`order/service.ts` 還用 `Promise.all` 平行送出各規格的庫存預留。

購物車只存規格與數量，每次讀取再取最新價格；正式建單時再留下價格快照。**能快取的長期快取，不能用舊值的資料就重新確認。**

我會這樣寫效能需求的範本：

```text
商品頁需要 SEO，請用伺服器渲染；購物車、結帳與訂單是個人頁面，不需要 SEO。
部署後前台與 API 優先使用平台的內部服務通道。
內容不變的靜態資源要能長期快取，更新時換網址。
需要強一致的庫存操作，把鎖的範圍縮到最小，不要讓全站排同一條隊。
獨立的規格預留可以平行處理，但失敗時必須釋放已預留的庫存。
列表都要分頁並限制上限；購物車不要把舊價格當成結帳依據。
請解釋每個設計的理由，不要用沒量測過的分數或速度證明成效。
```

## 四、金流：叫 AI 不要憑記憶

README 的 M3 開工前準備直接寫著：「不要憑記憶，以官方文件為準」。

AI 先查綠界開發者文件，整理成 `apps/api/src/modules/payment/README.md`，附來源與查閱日期 2026-10-12。官方 CheckMacValue 範例也變成單元測試的測試向量，也就是已知輸入與正確答案，用來核對簽章計算。

我實際下的 Prompt：

```text
把金流抽象化，至少包含 CreateOrder、HandleCallback、Refund、Query 四個方法，不要把廠商的欄位寫死在 domain model 裡。
```

結果是 `PaymentProvider` 介面，位於 `apps/api/src/modules/payment/provider.ts`。介面是各家金流都要遵守的共同約定；綠界專屬欄位的轉換留在 `ecpay/`，訂單核心只看共通資料。

這四個方法都有約定，但不代表退款已完成；M3 只開放信用卡付款，退款仍排在下一階段。

付款通知（webhook）是金流伺服器主動告訴商店付款結果，處理時還有幾道檢查：

- 簽章用常數時間比較，減少比對過程的時間差線索
- 通知金額必須等於資料庫的訂單總額
- 同一筆通知重送，不重複處理
- 綠界後台的「模擬付款」通知不改任何資料
- 每 10 分鐘排程對帳，補上可能漏掉的通知

**付款成功與否只相信伺服器對伺服器的通知，不相信瀏覽器跳回來的那一頁。** 通知漏掉時，再由伺服器呼叫查詢 API 對帳；回跳頁只負責帶顧客回訂單頁。

## 五、讓 AI 自己驗證，並且追問失敗流程

寫完不等於能收款。我實際下的 Prompt 是：

```text
你知道 Sandbox 資料了，自己去把綠界設定資料抓過來，然後自己起 server 來驗證結帳流程?
```

Sandbox 就是不會真的收款的測試環境。AI 在本機起了前台、後台、API 三個服務，透過 `cloudflared tunnel` 開臨時通道，讓綠界的付款通知能打回本機。

第一次付款失敗了。我接著問：

```text
失敗的話應該有失敗流程吧？那這個系統目前是怎麼處理這個失敗流程的？
```

確認失敗流程後，再建一筆新訂單，用綠界公開測試卡走完「刷卡 → 通知 → 訂單變已付款 → 導回訂單頁」。這是在測試環境驗證，還不是正式收款。

專案另有 67 個自動化測試，透過 Cloudflare 官方的 Vitest 整合，跑在本機真實的 Workers 執行環境。包含 **30 個請求同時搶 5 件庫存，必須剛好成功 5 筆**。

CI 是每次推送後自動執行的檢查流程；目前推送到 main 時會跑型別檢查、測試與建置，提出合併請求時也會跑。**成功流程要走完，失敗流程也要追問。**

## 六、聽不懂就問，問到能自己做決定

我實際問過這兩個問題：

```text
D1 存的是 UTC，但你應該可以向 rails 直接處理換成台灣時間，或是前端自己處理?
```

```text
怎麼做到回傳的 URL 可以轉到本地 localhost？是因為CF有類似 ngrok 的功能嗎？
```

第一個問題最後的決定是：資料庫一律存 UTC 這個統一時間基準，顯示與報表的「一天」則用台灣時區。`packages/shared/src/time.ts` 的 `SHOP_TIME_ZONE` 固定為 `Asia/Taipei`，報表切日也依這個規則規劃。

第二個問題讓我釐清臨時通道怎麼把公開網址接回本機，而不是看到網址能通就算了。

**問「為什麼」不是浪費 token，是讓自己之後維護得動。** AI 可以實作，但時區、付款與庫存的決定，我要能自己解釋。

## 七、做完之後，請 AI 當一次攻擊者

M3 做完後，我請 AI 把整個專案當成攻擊目標再看一次。它又找到一批可以更好的地方，已排進待辦：

- 安全標頭還沒完整設定，例如 CSP（限制可載入的內容）與 HSTS（要求使用 HTTPS）
- 限流目前只涵蓋登入與註冊
- 後台需要 Cloudflare Access 再加一道身分驗證，API 入口也要一起收斂
- CI 還沒有相依套件與金鑰掃描

**功能驗收通過，不代表資安審查結束。** 審查範本可以這樣寫：

```text
請在唯讀模式下，以攻擊者角度審查整個專案，不要直接修改檔案。
依嚴重度排序，每項附檔案位置、證據、影響與建議修法。
區分已確認、待驗證與平台設定無法從程式碼確認的項目。
報告不要包含可操作的攻擊細節或完整秘密；先讓我決定修正順序。
```

想先建立檢查觀念，可以讀[用 AI 做網站前，一定要知道的 5 個資安秘訣](/blog/ai-website-security-5-tips/)。

## 八、我的分工：AI 規劃、AI 實作、我驗收

Claude Code 負責讀程式、拆步驟、說明取捨，Codex 負責實作。我負責把需求說清楚、決定接受哪些限制，每次實作完都看 diff，也就是這次改了什麼，再重跑測試。

**AI 說「完成了」，只是驗收的開始。**

## 小結：可以帶走的原則

- 先拿到規劃與完成標準，再請 AI 寫程式
- 資安與效能是需求，要具體列出來
- 平台限制先談取捨，不要默默省略防護
- 金流看官方文件，付款結果由伺服器確認
- 驗證要包含成功、失敗、重送與同時搶購
- 不懂就問，實作完還要看 diff、跑測試、再做安全審查

下面是一份可以直接複製的起手式 Prompt 範本：

```text
我要做一個電商網站。先不要寫程式，請先交付架構文件。
說明技術選型與理由，切成里程碑，每階段列完成標準、驗證方式與已知限制。
資安需求：密碼加鹽雜湊、Session 只存雜湊、Cookie 設 HttpOnly／Secure／SameSite；
權限做在 API、輸入用 schema 驗證、SQL 參數化、上傳白名單、錯誤不外洩、
登入註冊限流、別人的資料回 404。每項都要有自動化測試。
效能需求：商品頁要 SEO，個人頁在瀏覽器渲染；服務間優先內部呼叫；
內容不變的靜態資源長期快取、更新換網址；庫存鎖縮到單一規格；
獨立預留平行處理但須能失敗回復；列表分頁設上限，價格由伺服器取最新值。
平台有限制時，先解釋取捨讓我決定。金流先查官方文件並記錄來源與查閱日期。
計畫確認後分階段實作，每階段提供 diff、測試結果與尚未驗證的項目。
```
